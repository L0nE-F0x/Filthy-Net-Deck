# Audit — v3.0.0 (2026-08-12)

Deep review of everything shipped since the last audit: **v2.7.3 → v2.8.2**,
8,848 insertions across 81 files. That span is the entire backend — accounts,
public profiles, crowd meta, deck sync, friends, public decks — plus the
opponent-inference rewrite. **None of it had been adversarially reviewed.**

Trigger: the owner is preparing a public push to an existing YouTube + X
audience, so the question was not "does it work for one user" but "what breaks
when several hundred people arrive at once, and what does the project claim that
is not true".

Scope: `v2.7.3..HEAD` for `src/`, `src-tauri/src/`, `pipeline/`, `supabase/`,
`netlify/`, plus every published claim. Measurements are from a production Vite
build served locally and verified in-browser, not from reading code.

---

## Verdict

Nine findings. One would have frozen the community data permanently, one was
costing every user continuous CPU, and three were things the project said about
itself that were not true.

| # | Severity | Area | Issue |
|---|----------|------|-------|
| 1 | **P0** | SQL | `rebuild_matchup_rollup()` can raise 23502 and silently freeze all community data |
| 2 | **P0** | React | Splash never unmounted — whole app tree re-rendered every 900 ms, forever |
| 3 | **P1** | Docs/site | README + 3 marketing strings promised "nothing is uploaded" for three releases after it stopped being true |
| 4 | **P2** | SQL | `public_profile_decks` published full decklists to `anon`, contradicting the product |
| 5 | **P2** | SQL | `shared_matches` had no server-side insert ceiling at all |
| 6 | **P2** | Rust | `rewrite_matches()` claimed crash-safety it did not have (no fsync before rename) |
| 7 | **P2** | UI | Settings consent copy named one upload path when there were two |
| 8 | **P3** | SQL | `friend_lines.best_rank` returned the *latest* rank, under a comment saying otherwise |
| 9 | **P3** | UI | Splash advertised "Matchup Lab", retired four releases earlier |

Also implemented: the §4 statistical-outlier exclusion, specified in the design
and never built.

## 1 · P0 — the rollup could abort and freeze the moat

```sql
round(0::numeric * least(0, cap) / nullif(0, 0))::int
  → 0 * 0 / NULL → NULL → round(NULL) → NULL
```

`a_on_play` is NULL for every row where the user was on the **"b" side** of the
canonical pair (`my_archetype > opp_archetype`), and also whenever
`games->0->>'onPlay'` is absent. Such a user has `on_play_games = 0`, so
`nullif(0,0)` makes their capped `on_play_wins` NULL.

If *every* contributor to one cell is in that state, `sum()` over all-NULLs is
NULL. The INSERT names the column explicitly, so `default 0` never applies, and
`a_on_play_wins int not null` raises 23502 — aborting the function, rolling back
the hourly cron, and stopping `matchup_rollup` for **every user**, silently.

It needs one matchup cell where all uploads came from players on the
alphabetically-later archetype. That is *more* likely with few contributors and
diverse pairings — i.e. exactly at launch, the worst possible moment.

**Not executed.** No Docker or psql on the machine and the Supabase CLI needs
Docker, so this is reasoned rather than run. It rests on three unambiguous
standard-SQL facts: `SUM` of all-NULLs is NULL; an explicit NULL in an INSERT
column list bypasses the column default; NOT NULL then raises.

**Fixed** in `20260812060000`: coalesce the per-user value *and* the sum.

## 2 · P0 — the splash never unmounted

The dismissal effect cancelled its own unmount:

```js
if (!ready || !minElapsed || fadeOut || gone) return;
setFadeOut(true);
const t = setTimeout(() => setGone(true), FADE_MS);
return () => clearTimeout(t);
}, [ready, minElapsed, fadeOut, gone]);
```

Setting `fadeOut` re-runs the effect → cleanup clears the pending timeout → the
`|| fadeOut` guard returns before scheduling another. `gone` never became true.

Nothing *looked* wrong: the CSS still faded the splash to opacity 0, so the app
appeared normally and the overlay was invisible and click-through. But it stayed
mounted for the life of the process, which defeated **both** mitigations written
into that very file — the tips interval is cleared on `gone`, and the wrapper
early-returns unwrapped children on `gone`. So every 900 ms the tips interval
re-rendered `SplashScreen`, whose children are the entire app.

This is precisely the failure the v2.7.3 audit documented — *"splash wrappers
that keep state + interval after exit will re-render the entire app"* — with the
fix present but unreachable. On a desktop tool meant to sit open all day beside
a game.

**Measured**, production build:

| | before | after |
|---|---|---|
| `.splash-root` in DOM 2 min after boot | yes, `opacity: 0` | absent |
| DOM mutations in a quiet 4 s window | **10** | **0** |
| tips still cycling | all 5 | none |

**Fixed** by splitting into two effects so setting `fadeOut` cannot cancel the
timer it starts. Covered by `SplashScreen.test.tsx` — verified against the old
code, where 3 of its 5 cases fail. A pure-logic test could not have caught this
(the defect was effect wiring), which is why the previous fix did not hold; that
required adding jsdom + testing-library, opted into per-file so the other 556
tests stay in the fast node environment.

## 3 · P1 — the project promised something untrue for three releases

`README.md` and three strings on the marketing site said *"nothing is uploaded
anywhere"* / *"never leaves your PC"*. Uploads shipped in **v2.7.5** (health
ping) and **v2.7.6** (match sharing).

`BACKEND-PHASE-2.md` §8 had said, in as many words, that the README gets
rewritten *"at the moment the first upload ships — not before"*. That moment
passed and nothing happened, because no release-checklist item owned it.

Worth being precise about the blast radius: the **in-app consent copy was
accurate throughout**, and that is what actually gates an upload — so nobody was
uploaded without consenting. What was wrong was the claim on the two pages a
*prospective* user reads first.

**Fixed:** all four strings corrected; `website/privacy.html` now publishes both
allowlists field by field; `AGENTS.md` carries a binding rule tying payload
changes to README + site + privacy page, with a checklist line.

## 4 · P2 — public decks published more than the product says

`public_profile_decks` selected `d.main` and `d.side` — the Arena card ids — and
is granted to `anon`. So the full list of any published deck was readable
straight off the REST API, while the product, the handoff notes and the new
privacy page all say a published deck shows *"format, size and last played —
not the list"*.

Its only consumer, `profile.mts`, used `.length`. So the exposure bought nothing
and also shipped ~75 integers per deck across the wire to compute two numbers.
**Fixed:** the view returns counts.

## 5 · P2 — no server-side upload ceiling

§4 specified "100 matches/day, 400/week". Nothing was implemented. The client
chunks at 50, but the client is in a public repo and the REST endpoint accepts
authenticated inserts directly — that is not enforcement.

The designed number was also unshippable: a new user backfilling a long local
history would fail their first sync at 100 and keep failing, punishing exactly
the users worth having. The 5% cell cap, trust gate and confidence floor already
bound *influence*, so what this limit is really for is **cost**.

**Fixed:** 2,000/day, keyed on server-set `created_at` — `ended_at` is
client-supplied and would be trivially forged.

## 6 · P2 — the data-loss repair path was not crash-safe

`rewrite_matches()` documented "a crash mid-write can't lose the surviving
history" but used `fs::write`, which never fsyncs. The rename could reach disk
while the temp file's data blocks had not, replacing good history with a
truncated file. Temp-file-plus-rename is only atomic if the data is durable
*before* the rename.

Small window, but this is the function whose entire reason for existing is that
**348 matches were lost once already**. **Fixed:** `File::create` + `write_all`
+ `sync_all()` before the rename.

## 7 · P2 — the consent copy under-counted itself

Settings → Data & privacy said the health ping was *"the one optional
exception"*. There were two, and the larger one — cloud sync, which uploads
matches and decklists — sits **above** it under Account. **Fixed**, and the
privacy page is now linked one click from the toggles.

## 8 · P3 — `best_rank` was the latest rank

`friend_lines` returned `array_agg(rank order by ended_at desc)[1]` under a
comment reading *"Highest rank REACHED, not current: this is a race, and what
people actually compare is how far up they got"*. The code did the opposite of
its own comment.

Nothing user-visible lied (the TS doc said "freshest", the column header said
"Rank"), but the next person to touch it would have believed the SQL.

**Fixed** by returning the distinct ranks and picking the max client-side with
`parseRank`'s existing 0–22 score — so `"Mythic 93.4%"` beats `"Mythic 82%"` and
`"Mythic #874"` beats any percentile, where a string sort disagrees. Doing it in
SQL would have meant a second copy of that parser, guaranteed to drift.

## 9 · P3 — the splash advertised a retired feature

"Warming up Matchup Lab…" — Matchup Lab was replaced by Matchups in v2.7.6.
Nothing pointed at that array, so it survived four releases. Now covered by a
test.

## What was checked and found healthy

- **The v2.7.3 perf lessons all held.** No page-level `React.lazy` (only the
  `main.tsx` App-vs-overlay/toast/presence split), no `startTransition` around
  Zustand `set`, no toast prewarm at boot, no `key={page}`. **5 JS requests at
  boot**, exactly where that audit left it.
- **Bundle:** App 389 kB / 116 kB gzip. The split that matters is intact —
  `OverlayApp` (30 kB), `ToastApp` (2 kB), `PresenceApp` (4.8 kB) are separate,
  so the three secondary WebView2 renderers still never parse the main app.
- **RLS posture is sound.** `public_profiles`, `public_profile_stats` and
  `public_profile_archetypes` expose curated columns only; raw `shared_matches`
  has no public read; the view-over-locked-table pattern is used correctly
  because RLS is row-level, not column-level. Only finding 4 deviated.
- **`deeplink.rs` and `install_id.rs` are clean** and well-tested.
- **The health-ping Edge Function** has an IP throttle with honest comments
  about being a speed bump rather than a control, and the real cap is the
  `(install_id, day)` primary key.
- **The archetype-FK deviation is correct.** The design specified FKs; the
  implementation uses a regex shape check, because a hard FK would reject a
  legitimate match whenever the registry lagged the feed and silently lose real
  user data. Deviation documented in the migration.

## Open, not fixed here

- **`MIN_MS = 1600` + `FADE_MS = 520` gates every launch behind ~2.1 s** even
  though boot completes in ~110 ms and first paint at 560 ms. That is a
  deliberate splash minimum and an aesthetic call, not a defect — but it is now
  the single largest startup cost in the app, and worth a decision.
- **Email OTP has no test coverage**, unlike the OAuth path. Hidden behind
  `EMAIL_SIGN_IN_ENABLED` for v3.0.0; both need fixing before it returns.
- **`emit` vs `emit_to` on the OAuth deep link** — tried, reverted, reasoning
  recorded in `deeplink.rs`. Same origin and process, so cosmetic; not worth an
  unverifiable risk to the sign-in path before a launch.
- **The 5% cell cap only stops binding at ≥20 contributors per cell**, so crowd
  cells fill slowly by construction. Working as designed; worth knowing before
  concluding the crowd meta is broken.
- **Disk:** `src-tauri/target/` ~9 GB, `.git` ~1.6 GB / 490 MB packed.
